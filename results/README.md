## Methods

Five compressions of the same operator appear across the experiments. The keys are the
column suffixes used in the CSVs; the labels are the ones used in the paper:

| Key | Label | Method |
| --- | --- | --- |
| `hmataca` | H, ACA | H-matrix, standard ACA (Frobenius-norm stopping criterion) |
| `hmatrs` | H, ACA-RS | H-matrix, ACA with the additional random-sampling criterion |
| `nca` | DH², NCA | directional H², wideband admissibility, plain tree mimicry pivoting |
| `ncaefie` | DH², NCA-EFIE | the same, with the EFIE directional filter |
| `ncaefieoct` | DH², NCA-EFIE (octree) | `ncaefie` on an octree instead of the k-means tree |

`hmatrs`, `ncaefie` and `ncaefieoct` are the three **error-controlled** compressions:
their stopping criterion tracks the true far-field error, so they attain the requested
tolerance. `hmataca` and `nca` do not -- their error stagnates about an order of
magnitude above `tol` and grows with N. The cube runs all five to show the difference;
the sphere and the rafale run only the three error-controlled ones.

Each method contributes four columns:

| Prefix | Quantity |
| --- | --- |
| `stor…` | storage of the compressed matrix, GB |
| `err…` | relative far-field error against the reference matrix on the same tree |
| `tass…` | assembly time, s |
| `tmv…` | fastest mat-vec of a repeated series, s |

## Provenance of the committed CSVs

`cube.csv`, `sphere.csv` and `rafalefuel.csv` carry the schema that `compareframe`
writes, but they were **not** produced by the current `simcompare.jl` in one pass. They
were assembled from the pre-refactor runs, which split the same experiment across
several files: a k-means accuracy run (`simfull.jl`, `simfailure.jl`) wrote a
`h2mat`/`hmat` column pair, the octree run (`simh2.jl`) went to a separate `*TN*` file,
and the timings were re-measured by their own campaign (`simtime.jl`).

Source of each column group:

| Column group | Cube | Sphere | Refined rafale |
| --- | --- | --- | --- |
| `…hmataca` | `cube_failure.csv` `*hmat*` | — | — |
| `…hmatrs` | `cube.csv` `*hmat*` | `sphereico.csv` `*hmat*` | `rafalefuel.csv` `*hmat*` |
| `…nca` | `cube_failure.csv` `*h2mat*` | — | — |
| `…ncaefie` | `cube.csv` `*h2mat*` | `sphereico.csv` `*h2mat*` | `rafalefuel.csv` `*h2mat*` |
| `…ncaefieoct` | `cubeTN.csv` | `sphereTNico.csv` | `rafalefuelTN.csv` |

(The pre-merge files are preserved in git at commit `f91dd0c`.)

Three caveats travel with this data. **A re-run of the current `simcompare.jl` resolves
all three**; until then they have to be quoted with the numbers.

1. **`tass…`/`tmv…` are single-threaded for the sphere and the rafale, everything else
   is parallel.** The timing campaign (`spheretime*.csv`, `rafaletime*.csv`) passed
   `SerialScheduler()`, so its assembly times are serial, while the `stor…`/`err…`
   columns in the same row come from multithreaded runs. Each timing column is the
   minimum over the repetitions of that size, taken independently per column -- the
   fastest assembly and the fastest mat-vec usually come from different repetitions.
   The cube has no timing campaign, so its `tass…`/`tmv…` are the parallel same-run
   times recorded next to its accuracy data and are *not* comparable to the sphere's
   and the rafale's.

2. **The `hmatrs` columns were run at a looser tolerance than their `tol` column
   claims.** `simfull.jl` hardcoded the H-matrix stopping criterion to
   `FNormEstimator(1e-2)` + `RandomSampling(tol=8e-3)` instead of passing `tol`, so
   these are ~1e-2 runs sitting in rows labelled `tol = 1e-3`. `simtime.jl`'s `hmat`
   branch used the same hardcoded settings, so the `hmatrs` timings are at least
   consistent with the `hmatrs` storage and error. This is also why `storhmatrs` can
   fall *below* `storhmataca` on the cube despite being the more accurate method.

3. **`errhmatrs` and `errncaefie` are full-matrix errors; the other three are
   far-field errors.** `simfull.jl` had its `farmatrix()` calls commented out
   (`farh2mat = h2mat#NestedCrossApproximation.farmatrix(h2mat)`), so those two columns
   divide by the norm of the full matrix rather than the far field. The near field
   cancels in the numerator either way, so the two columns are systematically smaller
   than the like-named quantity in `errhmataca`, `errnca` and `errncaefieoct`.

Every file in this directory is regenerated by a current script. The pre-merge
inputs, the superseded runs and the pgfplots mesh tables whose plotting scripts were
removed are all preserved in git at commit `f91dd0c`.

## Sphere

| File | Rows | Produced by | Parameters |
| --- | --- | --- | --- |
| `sphere.csv` | 6 | merged, see above | `hmatrs`, `ncaefie`, `ncaefieoct`; `γ=1.0`, `ηhf=5.0`, `tol=1e-3`, `meshicosphere(reff, 1.0)` for `reff ∈ {28, 40, 57, 80, 114, 160}`, N = 23520 … 768000 |
| `spheresweep.csv` | 36 | `sphere/spheresweep.jl` | `meshsphere(1.0, 0.025)`, N = 72270, `γ=1.0`, `tol ∈ [1e-2 … 1e-10]`, over `tree ∈ {kmeans, octree}` × `ηhf ∈ {1.0, 5.0}` |
| `rcs_xy_mie.csv` | 721 | `sphere/spheremie.jl` | RCS of the solved sphere vs. the analytic Mie series; `meshsphere(1.0, 0.017)`, `λ = 10h`, xz-plane cut over 721 angles |
| `solve_sphere_<N>.vtu` | — | `sphere/spheremie.jl` | surface current density of the same solve, for ParaView. `.vtu` is gitignored, so it is not committed |

`spheresweep.csv` holds all four sweeps of the 2×2 grid over cluster tree and
admissibility parameter, nine tolerances each. The first two columns select which
sweep a row belongs to:

| Column | Meaning |
| --- | --- |
| `tree` | `kmeans` or `octree` |
| `etahf` | `1.0` or `5.0` |
| `N`, `tol` | discretization size and requested ACA tolerance |
| `err` | relative far-field error against a dense reference on the same tree |
| `storage` | storage of the compressed matrix, GB |

It replaces the four files `spheresweep{,TN}{1.0,5.0}.csv` of earlier revisions; the
numbers are unchanged, only relabelled.

Note the sweep meshes with `meshsphere` while `sphere.csv` uses `meshicosphere`, so
the two are not row-by-row comparable.

`rafaleopen/rafaleopenfull.jl` writes the solved surface current density as
`openrafale_<N>_<mult>h.vtu`, for ParaView. `.vtu` is excluded by `.gitignore`, so
the file is not committed. Neither that script nor `sphere/spheremie.jl` stores the
solution vector itself -- it is only an intermediate on the way to the files above.
